# 38 项定义：问法、判定与落位

每项格式：**问什么 → 典型答案 → 判定（怎样算问清了）→ DSH 落位**。

---

## 域 1：产品目标与范围（P01–P04）

### P01 服务谁
- **问**：这个 agent 替谁办事？只你一个人、你多台设备、还是多人共用？
- **典型**：单人本机 Web；若给多人用，必须另定义会话与数据隔离，不能简单共用地址。
- **判定**：能明确"几个人、什么身份、是否需要隔离"。
- **落位**：影响记忆作用域、工具权限、是否需要按用户分区。

### P02 解决什么问题
- **问**：把"现在交代一件事 / 长期目标 / 定时工作 / 看建议 / 看产物"分开——它负责哪几个入口？
- **典型**：只负责"现在交代一件事"里的售后咨询；不做长期目标、不做定时。
- **判定**：能列出**首批 3–5 个真实任务**，而不是能力宣传。
- **落位**：任务类型决定挂哪些工具（见域 2）。

### P03 交付什么结果
- **问**：结果长什么样？聊天结论、文件产物、已保存计划，还是真实操作完成？
- **典型**：聊天结论 + 一张可转发的转人工摘要；不生成文件。
- **判定**：能说出"用户拿到什么就算这件事办完了"。
- **落位**：决定是否需要 `dsh-tool-present`、是否需要写操作工具。

### P04 第一版边界
- **问**：边界分三层——源码有能力 / 本实例已接好 / 这个版本愿意开放。第一版只做哪层？
- **典型**：只开放"已接好且愿意开放"的；源码里有但没接的不算。
- **判定**：三层能分开写，不用"欢迎页承诺"扩范围。
- **落位**：preset 的 `plugins` 清单就是边界本身——没挂的调不到。

## 域 2：任务执行（P05–P09）

### P05 怎样开始任务
- **问**：用户怎么发起？打字、传附件、还是点快捷入口？
- **典型**：只接受打字；不支持附件（因为不挂多模态）。
- **判定**：起点的校验、上传、状态反馈都有交代。
- **落位**：是否挂 `dsh-tool-fs`、是否需要图片输入。

### P06 每类任务怎样完成
- **问**：把任务分成几类？每类的完成路径一样吗？
- **典型**：三类——直接答复（政策问答）、工具查询（查单）、带动作（建退款单）。不能要求都走"规划—执行—汇报"。
- **判定**：每类都能说出"完成的最后一步是什么"。
- **落位**：决定 persona 流程骨架 + 工具编排。

### P07 什么时候询问用户
- **问**：三种交互分开——回答一个问题 / 批准一个动作 / 用户亲自接管。本 agent 各在什么时候用？
- **典型**：缺订单号 → 提问；提交退款单 → 批准；短信验证码 → 本人在手机上接管（本 agent 不接）。
- **判定**：三种各有明确触发条件，不混用。
- **落位**：`dsh-tool-ask-user`、写操作前复述确认。

### P08 执行中怎样处理变化
- **问**：用户中途追加、纠正、停止、清空历史——分别怎么处理？
- **典型**：纠正只影响后续；已提交的动作不自动撤销；停止即终止本轮。
- **判定**：能说清"已发生动作不自动回滚"。
- **落位**：persona 声明；写操作工具要可查状态。

### P09 怎样结束和处理失败
- **问**：结束时要不要同时交代业务结果和运行状态？哪些失败必须说清？
- **典型**：结束要说"办成了什么/没办成什么"；工具失败、超时、断线分别有说法。
- **判定**：失败语义有清单（查不到、超时、权限不足、上游 5xx）。
- **落位**：工具返回结构化错误；persona 规定不许把失败说成成功。

## 域 3：上下文管理（P10–P13）

### P10 本次任务需要知道什么
- **问**：这一轮它需要哪些信息才能答？系统规则、用户请求、个人信息、工具协议，缺哪个会答错？
- **典型**：需要订单数据 + 售后政策 + 用户诉求；缺订单号就必须先问。
- **判定**：能列出"缺哪项就必须停下来问"。
- **落位**：工具入参必填项 + persona 澄清规则。

### P11 哪些要求必须一直保留
- **问**：哪些约束不能因为对话变长就丢？（禁止赔付、必须转人工等）
- **典型**：禁答清单与转人工条件是硬约束，任何轮次都有效。
- **判定**：能指出"即使上下文被压缩也必须保留"的条目。
- **落位**：写进 persona（每轮都在 system prompt 里），不要只写在对话开头。

### P12 任务之间怎样隔离
- **问**：多个用户/多个任务共用实例时，什么共享、什么必须隔离？
- **典型**：单用户时不用隔离；一旦多人必须按用户隔离记忆与会话。
- **判定**：能明确"共享哪些、隔离哪些"。
- **落位**：记忆文件按用户分区；会话独立。

### P13 信息不足或过期时怎么办
- **问**：不存在、没接入、读取失败、缓存旧、确实无结果——这五种要分开呈现吗？
- **典型**：必须分开；不能把"没接入"说成"查不到"。
- **判定**：五种状态各有话术。
- **落位**：工具错误码区分；persona 规定不许用"再问一次"代替证据。

## 域 4：长期记忆（P14–P17）

### P14 记什么、不记什么
- **问**：记忆里放什么？（短事实：偏好、未结事项、称呼）绝不记什么？（证件号、卡号、密码）
- **典型**：记"偏好上门取件""上次工单号"；不记身份证、银行卡、完整地址。
- **判定**：能列出白名单与黑名单各 3 条以上。
- **落位**：MCP 记忆服务；黑名单写进 persona 禁令。

### P15 什么时候记住
- **问**：自动记 / 每条询问 / 只在你明确说"记住"时才记？
- **典型**：默认"只记明确要求的 + 关键未结事项"，其余不记。
- **判定**：三档选一，并说明理由。
- **落位**：persona 规定写入时机；写入前复述。

### P16 事实变化怎样处理
- **问**：用户更正了之前的信息，是覆盖、并存、还是标记冲突？
- **典型**：覆盖旧条目并保留一条"已更正"记录。
- **判定**：能说明"旧事实怎么处理"。
- **落位**：记忆服务的 add/delete；persona 规定先删后写。

### P17 用户怎样控制记忆
- **问**：用户能看到记了什么吗？能忘掉吗？忘掉是移除还是彻底删除？
- **典型**：可查看、可忘掉、可撤销；"忘掉"是移出活跃记忆，不等于物理擦除。
- **判定**：能说清"忘掉"的语义边界。
- **落位**：`mcp__memory__*` 的 read/delete 工具；话术不得承诺彻底删除。

## 域 5：工具与权限（P18–P22）

### P18 开放哪些能力
- **问**：把能力清单列出来，哪些是本任务真要用的？
- **典型**：只开查单、查退款、建单；不开 shell、文件、网络。
- **判定**：能力清单与"愿意开放"清单分开。
- **落位**：preset 的 `plugins`；工具越少越安全。

### P19 允许操作哪些对象
- **问**：许可要落到对象——哪些订单、哪些目录、哪些账号、哪些联系人？
- **典型**：只能操作本店铺订单；不能跨店铺。
- **判定**：能说出对象范围，而不只是工具名。
- **落位**：工具内部校验对象归属；越界返回拒绝。

### P20 哪些操作可以直接执行
- **问**：哪些动作不用问就能做？（通常是只读）
- **典型**：查询类直接做；写操作一律确认。
- **判定**：能列出"免确认清单"。
- **落位**：只读工具 vs 写工具分开注册。

### P21 哪些操作需要确认
- **问**：确认卡要绑定什么？（本次动作 + 具体对象 + 金额）
- **典型**：建退款单前必须展示单号、理由、金额，用户点头才提交。
- **判定**：确认内容能落到具体字段。
- **落位**：persona 的复述规则 + 写工具前置条件。

### P22 允许怎样向外发送数据
- **问**：外发分四种——模型请求、工具外发、上传、同步。本 agent 允许哪些？发到哪？
- **典型**：只把必要字段发给模型；不调用任何外部 webhook；不上传文件。
- **判定**：能说出"什么数据会离开本机、去哪"。
- **落位**：不挂 `dsh-tool-web`；MCP 只连本机服务。

## 域 6：数据接入（P23–P26）

### P23 接入哪些来源
- **问**：每个来源的协议、能读写什么、当前是否已经接好，分开登记。
- **典型**：订单库只读（HTTP）；工单系统可写（HTTP）。当前先用 mock。
- **判定**：每个来源三列都有值。
- **落位**：每源一个工具或一个 MCP server。

### P24 使用什么身份
- **问**：登录身份、模型端点身份、工具执行许可——三套边界分别是什么？
- **典型**：工具用服务账号只读；模型用平台 key；两者不混用。
- **判定**：能说清"换端点不能带走旧密钥"。
- **落位**：凭证走 credentials 服务；不写进 YAML。

### P25 怎样获取和更新数据
- **问**：保存连接、测试连通、取实时数据、写入成功——四个回执要分开吗？
- **典型**：必须分开；"连通"不等于"能读业务数据"。
- **判定**：四种状态各有判定方式。
- **落位**：工具返回明确状态码；验收分开测。

### P26 数据经过哪里、保存多久
- **问**：会话、记忆、缓存、审计各保留多久？用户能删吗？
- **典型**：会话随工作区；记忆 6 个月；无云端副本。
- **判定**：每一层都有保留期与删除方式。
- **落位**：记忆文件路径与清理策略。

## 域 7：后台任务（P27–P30）

### P27 是否允许主动工作
- **问**：主动推进、明确提醒、到时执行、Feed 批次——分别授权哪一个？
- **典型**：第一版只做"到时提醒"，不做主动推进。
- **判定**：四种意图分别表态，不用一个总开关概括。
- **落位**：`dsh-tool-schedule`；`dsh-tool-goal` 按需。

### P28 什么条件触发
- **问**：触发要有精确字段、匹配语义、时间范围、唯一键。你的是什么？
- **典型**：每天 10:00 提醒查未结工单；按工单号去重。
- **判定**：能写出可执行的触发规则。
- **落位**：schedule 的 rrule 与 payload。

### P29 什么时候打扰用户
- **问**："安静"不是所有通知消失。每种后台任务何时执行、是否通知、通知去哪？
- **典型**：只在工作时段通知；夜间只记录不推送。
- **判定**：每种任务都有执行/通知两列。
- **落位**：schedule target 与会话策略。

### P30 错过或失败怎样处理
- **问**：出错、被停止、进程崩溃、错过周期——恢复方式不同，分别怎么办？
- **典型**：错过补跑一次；失败记录并在下次提醒时说明。
- **判定**：四种情况各有处理。
- **落位**：任务幂等 + 状态记录。

## 域 8：入口与部署（P31–P34）

### P31 用户从哪里使用
- **问**：Web、桌面壳、手机、IM 通道——第一版真正交付哪个？
- **典型**：只交付本机 Web；其他端不算已支持。
- **判定**：能明确"只有这个入口算数"。
- **落位**：profile 捆绑的 app（web / headless / acp）。

### P32 在哪里运行
- **问**：本机回环？服务器？别人怎么访问？关网页等于关机吗？
- **典型**：本机回环；关浏览器不等于停服务。
- **判定**：部署边界清楚。
- **落位**：`dsh web` 的 host/port 与访问控制。

### P33 用户怎样看到进度并介入
- **问**：进度不只有聊天回复。步骤卡、待批徽标、问题卡、失败提示分别承担什么？
- **典型**：工具调用要有可见步骤；待确认时有明确提示。
- **判定**：每种介入方式都有触发点。
- **落位**：DSH 的轨迹与审批 UI；工具描述影响展示。

### P34 怎样表达结果
- **问**：回复语言、语气、界面语言、产物格式——分别要求什么？
- **典型**：中文、口语化、纯文本、不生成文件。
- **判定**：四列都有答案。
- **落位**：persona 的语言与格式约束。

## 域 9：模型、成本与验收（P35–P38）

### P35 需要什么模型能力
- **问**：模型可连、工具可用、完成真实任务——三层验收。你需要哪层？
- **典型**：三层都要；只测"可连"不算通过。
- **判定**：三层分别有验收方法。
- **落位**：模型选择 + 工具调用测试。

### P36 可以接受多少等待和费用
- **问**：单次等待上限？token 上限？预算耗尽时怎么收尾？
- **典型**：单轮 60 秒；超时要说明已做到哪一步。
- **判定**：三个数字 + 一个耗尽行为。
- **落位**：模型与 profile 的预算配置。

### P37 怎样证明做对了
- **问**：验收以什么为证据？（真实数据、执行记录、界面一致）
- **典型**：工具真被调用 + 返回真实数据 + 用户可核对。
- **判定**：能给出可复现的验收步骤。
- **落位**：验收清单，逐条跑。

### P38 哪些问题会阻止上线
- **问**：区分当前确认的缺陷、环境假设、尚未执行的能力测试，按风险阻断对应范围。
- **典型**：编造订单状态 = 阻断；转人工渠道未接 = 阻断。
- **判定**：能列出阻断项清单。
- **落位**：交付报告里的「未证明」部分。

---

## 域 10：行为契约（AGENTS.md）

把上面 38 项里**每轮都要生效**的部分抽出来，写成工作区的 `AGENTS.md`：

- 禁答清单
- 转人工触发条件与摘要格式
- 工具调用顺序（先说明再执行）
- 失败与不确定时的统一话术
- 记忆写入的确认规则

其余（流程细节、工具 schema）留在 persona 与工具定义里。**AGENTS.md 放"永远为真"的约束，persona 放"这个 agent 怎么说话"，工具放"能做什么"。**
